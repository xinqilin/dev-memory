三個名詞是什麼誰寫放在哪
對話 你跟 AI 講過的話，原始素材 自動收 只在你的電腦，不進 git
卡片 一個決定濃縮成三行：原因、決定、放棄了什麼 AI 起草，你確認 團隊 repo，只新增不修改（個人模式只留在本機）
頁面 一篇給人讀的文件，一個主題一頁 AI 寫，你在審核頁核准 團隊 repo

你只要會三句話

用平常講話的方式講，對應的 skill 自己會被叫起來。真正要你主動開口的只有第三句。

AI 問你要不要存
好，存吧 AI 做出決定時會主動提議，起草一張卡片給你看，你說可以才存。約 30 秒。
想查以前的決定
我們之前為什麼改成不中斷？ 直接問就好。它先翻記憶（文件 → 紀錄 → 原始對話），翻不到才去讀程式碼。
功能做完，要留文件
幫我寫一份發票拋轉 ERP 的文件 全程約 10 分鐘，中間停兩次等你回話。這是唯一會產生 PR 的一句話。想確定叫到它，就打 /dev-memory:wiki-ingest。

文件的事實來自程式碼，不是對話。欄位、必填、狀態值、cron 都從程式碼 repo 讀（每個 repo 讀哪支分支寫在 repos.yaml；用 git show，不切你的分支）；對話紀錄只拿來寫「設計考量」與 Known Issue。

三層式架構：借自 LLM Wiki

核心想法來自 Karpathy 的 LLM Wiki：不要每次問問題都從頭翻原始資料，而是讓 LLM 維護一層整理過的內容，人只負責把關。前面的三個名詞就住在這裡：對話和卡片在原始層，頁面在文件層。

往上長，往下找

寫文件時往上長：對話 → 卡片 → 頁面，越往上越濃縮。每上一層都有人點頭，錯的東西不會自己爬上去。

查東西時往下找：先看文件層，不夠再翻卡片，最後才翻原始對話。搜尋權重就照這個順序：文件 ×3 ＞ 紀錄 ×2 ＞ 對話 ×1。

規則層只在寫入時用到：AI 動筆前必讀，查東西的人完全不用知道它。

這一層裡面有什麼誰寫能不能改
規則層 schema.md（文件怎麼寫、來源優先序）、repos.yaml（產品有哪些 repo） 人 隨時改。改這份 markdown 就等於改 AI 的行為，不用改程式、不用發版
文件層 README.md 唯一索引、spec/ 主題文件 AI 寫，人在審核頁核准 可以改寫：就地更新，舊版本留在 git 歷史
原始層 records/*.jsonl 卡片、本機的完整對話 自動收，卡片由人確認 只增不改，所以每句話都追得回源頭

跟 LLM Wiki 最大的差別：我們的原始層不是事實。原作的原始素材（PDF、網頁）就是事實本身；我們的對話跟紀錄記的是當初的提案，真正的事實在程式碼，而且天天在變。所以多掛了第四個來源：程式碼是第一來源，紀錄只負責解釋「為什麼」。

中文怎麼搜得到：bigram ＋ unigram

中文沒有空白，整句會被當成一個詞，所以原本的工具搜不到。存進去之前先自己切成小積木，不靠詞庫、不靠模型。

bigram：兩字一塊，重疊切 例外外處處理
unigram：每個單字另外存一份 例外處理
程式名字：整個留著，另外拆開 invoiceStatus→ invoicestatusinvoicestatus

你平常不會自己打搜尋：你問 AI「之前為什麼⋯⋯」，或叫它寫文件的時候，是它在背後搜。下面是它實際會搜的字：

AI 搜的字會拆成結果
中介表中介、介表找到所有提到中介表的紀錄
發票拋轉為什麼不中斷發票、票拋、拋轉……中斷對上越多塊的排越前面；「什麼」這種到處都有的塊幾乎不加分
表表要靠單字那一份，才找得到「中介表」「排程表」
statusstatus找得到寫著 invoiceStatus 的紀錄

為什麼用 bigram，不用斷詞器

jieba 這類斷詞器靠詞庫，遇到新詞、專有名詞就認不出來，詞庫還要有人維護。重疊切法保證任兩個相鄰的字都會變成一個 token，不需要知道詞的邊界在哪。

代價是索引變大、偶爾誤中（查「中斷」撈到「途中斷了」），靠排序壓下去。

為什麼還要加 unigram

只存 bigram 時，一段中文的最後一個字不會是任何一塊的開頭。「更新中介表」切成 更新 新中 中介 介表，查「表」就漏掉。

加上 unigram 之後，實測查「表」從 341 筆變 423 筆，「中介表」「排程表」以前全部漏掉。

排序用 SQLite 內建的 bm25：命中越多、詞越罕見、文件越短，分數越高。沒有向量、沒有 embedding 模型，所以隊友只要裝 Bun 就能用，查一次不到 10ms、不花 AI 額度。

為什麼沒有用 embedding 模型

被問到時，「本機跑不動」是最弱的理由，它聽起來像做不到。真正的理由是設計上的，最強的在最前面。

① 搜尋結果是給 AI 看的，不是給人看的embedding 的價值是「你打模糊的字，系統猜你要什麼」。但這裡打字的是 AI：它會自己換詞重搜、先讀索引再決定關鍵字。語意那一層已經在它腦袋裡了，再塞一個小模型進去是同一件事做兩次。
② 要搜的大多是程式名字erp_sync_record 這種罕見詞正是 bm25 的強項；embedding 反而會把 InvoiceCountRequest 跟 InvoiceCountResult 當成幾乎一樣的東西，但它們在文件裡是不同階段。
③ 搜不到時查得出原因「查『表』會漏掉最後一個字」能定位到切詞方式，修完 341 筆變 423 筆，有數字可比。向量只給你一個距離，沒有下一步。
④ 零依賴才裝得起來整條搜尋路徑第三方依賴是 0，隊友只要有 Bun。要 embedding 就多三樣東西要裝，每一樣都是「跑不起來」的來源。團隊工具的採用率上限，是它的安裝成功率。
⑤ 索引隨時能重建，向量不行切詞方式改了，重建一次就好（0.9 秒）。向量只有同一個模型同一個版本可比，每個人裝的版本不同，索引就不能共用、不能一起 commit。
⑥ 瓶頸不在搜尋這個量級的資料，關鍵字已經接近可用上限。真正決定好不好用的是文件本身寫得好不好。

誠實的反面：「我要找那個處理退款失敗重試的東西」，但完全想不起任何程式名字、用的詞又跟文件不一樣——這種問法現在搜不到。緩解是 AI 會自己換句話重搜，而且 README 是唯一索引，真的找不到就整份讀完再決定。

一句話：檢索層要的是精確、可解釋、零依賴、可重建；語意理解交給已經在現場的 AI。要加 hybrid（兩種排名融合）不用動資料，多一張表就好——所以這不是放棄 embedding，是先做了那個不加也能用、加了也不用重來的部分。

可以放心的地方

原始對話不離開你的電腦放在 ~/.dev-memory/，不進 git；看起來像金鑰的字串收進來之前就遮掉，也可以列出整個不收的目錄。會給全隊看的只有卡片跟文件（卡片只送在這個產品的 repo 裡存的），而且都要過審核頁與 PR。
AI 碰不到送出push 跟開 PR 只有你能按，AI 從頭到尾不會替你 push。
背景收集零成本每回合存對話是純程式在搬檔案，不呼叫模型，也沒有常駐程序。
壞掉不會拖垮你記憶的錯誤全部吞掉、寫進 hook.log，不會讓你的對話中斷；dm setup 會列出最近的失敗。但本機資料庫不要刪：原始對話檔 Claude Code 預設 30 天就清掉，之後只剩這一份，要備份。
不要了也不會掉卡片整份文件不要了，跟 AI 說「這份不要了」。它會先把卡片退回本機，下次寫文件再帶上，然後才清掉工作區。
卡片檔衝突：兩邊都保留同一個人同時開兩個都有新卡片的 PR，後 merge 的會在卡片檔衝突。行的順序沒有意義，兩邊都留就對了；少留一邊，卡片會悄悄消失。

上手四步

1　裝工具
brew install bun gh && gh auth login個人模式只要 bun，不用 gh。
2　裝 plugin
claude plugin marketplace add xinqilin/dev-memory claude plugin install dev-memory@dev-memory Codex 要在 /hooks 信任一次，然後重開 session。
3　clone 文件庫
團隊共用的文件 repo，clone 到哪都可以。只想自己用就跳過。
4　跑一次 setup
dm setup --repo ~/project-other/<文件庫> # 團隊模式 dm setup # 個人模式：只收對話、搜尋、存卡片 建索引、灌既有對話、同步隊友的文件、逐項檢查環境。做完就能用了。缺什麼它會直接說要跑哪一行。
