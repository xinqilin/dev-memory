為什麼要做

記憶會蒸發

Claude Code 的對話紀錄預設 30 天就清掉。半年後想問「當初為什麼這樣決定」，沒有人答得出來，只能重新踩一次坑。

文件是額外工作

做完功能還要再寫一次文件，沒有人有動力。寫完了，程式碼一改又過期，也沒人回去更新。

知識散在各個 repo

一個功能橫跨 batch、api、frontend。改了一張資料表，誰在讀它、會影響誰，得靠人記。

原本的工具搜「例外」 找到 3 筆 ✕ 漏了 9 筆
實際上有 12 筆 ✓ 現在 12 筆全中

搜不到就等於沒有

原本的記憶工具不會斷中文，搜「例外」只找到 3 筆，實際有 12 筆。找不到的記憶，跟沒記一樣。

它怎麼運作

第 1 步

自動記日記

每講完一回合，對話就存進你電腦裡的 memory.db。原始對話只留在你這台。這一步純粹是程式在搬資料，沒有用到 AI。

搬的是對話紀錄檔，不是設定檔：~/.claude/projects/*/*.jsonl 跟 ~/.codex/sessions/…/rollout-*.jsonl。這兩個工具本來就會把每個 session 寫成 JSONL，plugin 只是照 byte offset 增量讀新增的行並記住讀到哪。settings.json 完全沒碰。

存進去時，中文兩字一塊＋單字 例外外處處理
查「例外」 例外 找到 12 筆，跟逐字比對一樣多
程式名字整個留著，也拆開 sapStatus→ sapstatus
第 2 步

中文也搜得到

問 AI 以前做過什麼，它會先翻這本日記。中文、英文、程式名字混在一起也找得到。翻找本身是資料庫在做，AI 只負責把找到的東西講給你聽。

不是 LIKE '%例外%'，是 SQLite 的 FTS5 全文檢索：where fts match ? order by bm25(fts)。LIKE 要逐筆掃全表而且沒有相關度；FTS5 是倒排索引，查 token 直接命中，再用 bm25 排序。

第 3 步你點頭才存

挑出重點卡片

做出決定時 AI 會主動提議（也可以自己叫 /mem-save），把對話濃縮成卡片——一張卡片就是一個決定，只寫三件事：為什麼、決定什麼、放棄了什麼。你看過、改過才存。

第 4 步確認點 ①

讀程式碼，給你骨架

AI 去讀 controller、DTO、enum、排程設定，然後列出這份文件打算長什麼樣：分幾節、哪節有 payload、哪節有圖。你點頭，它才動筆。

第 5 步確認點 ②

在審核頁改到滿意

瀏覽器自動打開本機審核頁。一次看全部檔案、跟 main 比、看這次一起送出的卡片。你改、叫 AI 改、用 IDE 改都行。

第 6 步

你自己按送出

在審核頁按「送出 PR」，或自己打 dm publish。PR 作者是你本人。AI 從頭到尾不會替你 push。

第 7 步

隊友同步，就搜得到

PR 合併後，隊友 sync 一下，不管用 Claude Code 還是 Codex，都查得到你的決定。

那我到底要做什麼

照平常的方式用 Claude Code 或 Codex 就好，什麼都不用改。有兩條路同時在跑：一條你完全不用管，一條偶爾需要你回一句話。

上面那條從你裝好的那一刻就沒停過，跟你有沒有做下面的事完全無關。下面那條綠色是你主動開口，藍框是它停下來問你。

上面那條是怎麼跑起來的

靠兩個 hook——兩個工具都支援的「發生某件事時幫我執行一行指令」機制。裝 plugin 的時候一起註冊，不用你設定。

hook什麼時候跑做什麼
Stop 每講完一回合，AI 回答結束的那一刻 把這個 session 的逐字稿檔案新增的部分讀進 memory.db。這是主要的收集路徑
SessionStart 每次開新的 session 補掃兩個工具的所有逐字稿，撿回上次漏掉的（當機、強制關掉都會漏），再把「索引裡有什麼、記得先搜記憶」這段話交給 AI

三個設計上的細節

只讀新增的部分

每個逐字稿檔案記著上次讀到第幾個 byte，下次從那裡接著讀，而且只吃完整的行——寫到一半的那行留到下次。所以不管跑幾次都不會重複，也不會半筆資料進去。

檔案變小就代表被換掉了，游標歸零重讀。

壞掉也不會拖垮你

Stop hook 裡所有錯誤都被吞掉、只留一行 log，最後一定 exit 0。記憶壞掉不該讓你的對話中斷——它只是個旁邊的東西，不是主線。

為什麼是 Stop 不是 SessionEnd

SessionEnd 只有 1～3 秒，來不及寫完就被砍。Stop 每回合都跑一次，每次只處理一點點，所以永遠來得及——而且你中途關掉視窗也已經存好了。

花多少錢：零。這兩個 hook 是純程式在搬檔案，沒有呼叫任何模型。沒有常駐程序、沒有定時任務——Stop 跑完就結束了。

哪些自動、哪些要你點頭

最容易誤會的一點：「存對話」跟「存卡片」是兩件不同的事。

誰觸發你要做什麼為什麼這樣設計
對話存檔 完全自動（Stop hook，每講完一回合） 什麼都不用做 只存在你電腦裡，不可逆也無害。索引裡那幾千筆對話，你一次都沒開口過
卡片 AI 會主動提議，但要你點頭 說一句「好」，或改一改再存 卡片會進團隊 repo（個人模式只留在本機）、只增不改，而且會變成未來文件的「設計考量」——錯的卡片比沒有卡片更糟
寫文件 只有你能開口 說「幫我寫一份〈主題〉的文件」 只有你知道現在這個主題值不值得寫成一頁

你不用記得要存卡片。 每個 session 開始時，plugin 會告訴 AI：「做出決定時——原因、決定了什麼、放棄了什麼——主動提議存起來」。所以是它問你，不是你想起來。而 mem-save 的規則寫死一句：沒給使用者看過的卡片，不准存。

你會講的話

下面五句裡，真正要你主動開口的只有第三句（寫文件）。第一句是回應 AI 的提議，第二句就是平常問問題，最後兩句很少用。用平常講話的方式講就好，對應的 skill 自己會被叫起來。

想要確定叫到它，就打斜線指令：/dev-memory:wiki-ingest。格式是 /plugin名:skill名，五個都可以叫：mem-save、mem-search、mem-setup、wiki-ingest、wiki-lint。用講的比較自然，但關鍵字沒對上時斜線指令是確定的。

AI 問你要不要存
好，存吧 通常是 AI 先開口問。mem-save 會起草一張卡片：原因、決定、放棄了什麼，印出來給你看，你說「可以」才存進本機。約 30 秒。
它沒問但你覺得值得記，也可以自己講「把這個決定存起來」。
想查以前怎麼決定的
我們之前為什麼改成不中斷？ 這句不用特別交代，直接問就好，mem-search 會自己被叫起來。它會先翻記憶（文件 → 紀錄 → 原始對話），翻不到才去讀程式碼。答案如果是從好幾筆紀錄或原始對話拼出來的，它會問你要不要存成一張卡片；文件還是一個主題寫一份。
功能做完，要留下文件
幫我寫一份測評點數拋轉 ERP 的文件 wiki-ingest：讀程式碼 → 給你骨架 → 寫文件 → 開審核頁。中間停兩次等你回話，全程約 10 分鐘。這是唯一會產生 PR 的一句話。主題要具體：一支批次、一條資料流、一個子系統。
文件放一陣子了
幫我檢查文件 wiki-lint：壞連結、沒被 README 索引的文件、重複的標題、程式碼改了但文件沒跟上。一個月跑一次就夠。
裝好了，或壞掉了
幫我設定 dev-memory mem-setup：檢查 bun／git／gh／索引／團隊 repo（沒設定團隊 repo 就是個人模式），缺什麼直接告訴你要跑哪一行。裝完跑一次，之後只有出問題才用得到。

第二句以外的四句，你不講它就不會做。沒有背景程序在偷跑，也不會自己開 PR。唯一永遠在動的只有「每回合把對話存進本機」，那一步不花 AI 額度。

它會先去讀程式碼

給骨架之前，它已經讀過 controller、DTO、enum、entity、排程設定。用 git show 讀，不會切你的分支——那是你正在工作的 repo。

本機 repo 在哪，查 ~/.dev-memory/config.toml。跑 dm repos 會自動掃常見目錄並列出找到沒有，缺的直接印出要貼的那一行。

四種動作

新增文件　沒有任何一頁講這件事
更新既有文件　已經有，這次是補充
補一節　只動其中一段

確認點 ②：審核頁怎麼用

這是唯一一個你會離開對話視窗的地方。它會印一個 http://127.0.0.1:隨機port/?token=… 的網址並自動開瀏覽器——只有你這台連得到，網址帶 token，關掉視窗就結束。

1 左邊那一排是檔案，不是卡片。常見誤會：看到好幾個會以為要挑。不用挑——文件本體、紀錄原文、README 索引，少了任何一個就會斷掉，所以它們一起 commit。真的不想要某一頁，按「捨棄這頁」。整份都不要了，跟 AI 說「這份不要了」，它會先把卡片退回本機，再清掉工作區。
2 四個分頁，至少看前兩個。「編輯 / 預覽」讀內容；「跟 main 比較」看到底動了什麼，更新既有頁面時最有用；「來源紀錄」列出這次一起送出的卡片原文，拿來對照「設計考量」寫的是不是真的有人說過；「檢查結果」平常是空的。
3 左半邊直接打字就能改。不用開 IDE。你改、AI 改、你在編輯器裡改，三邊都可以同時進行——外面被改到時頁面會問你要留哪一版。
4 右半邊是隊友會看到的樣子。即時跟著左邊變，就是 GitHub 上的樣子。
5 核准並 commit——commit 在本機，還沒上 GitHub。按不下去代表有檢查沒過，去「檢查結果」分頁，點檔名就跳過去修。疑似金鑰、壞掉的卡片檔、沒有標題的文件會在這裡被擋下來；疑似個資、殘留的 frontmatter 只提醒不擋。
6 送出 PR——這一顆才會 push。會再跳一次確認。按之前是灰的，因為還沒有東西可以送。只有你按得下去，AI 碰不到這顆。

PR 合併之後還有最後一步：跑 dm sync（或跟 AI 說「PR 合併了，幫我跑 sync」），合併的內容才會進你的本機索引。這一步不會自己發生——開 session 時自動做的是「補收漏掉的對話」，不是「拉團隊的新文件」。隊友也一樣，各自 sync 各自的。

你說一句話之後，它做了什麼

從你開口到預覽頁出現，中間有九步。你只在第六步回一句話。

為什麼第 ③ 步是整件事的關鍵

前面兩步只是找路，第三步才是文件跟事實對齊的地方。API 的欄位、必填規則、狀態值、cron 運算式——這些只有程式碼知道。

而且是每次寫文件都重讀一次，不是靠快取或記憶。程式碼改了，下次寫出來的文件就跟著改。

為什麼第 ⑤ 步值得特別做

實際跑第二篇的時候，sap-create-bu-data 跟既有的測評點數文件有一半重疊。正確的產出是只寫沒寫過的那一半，重疊的地方留一句「見某某文件」。

文件庫會爛掉，多半不是因為寫得不好，是因為同一件事散在三個地方，改的時候只改了一個。

資料從哪來、存到哪

文件的事實來自程式碼；對話只負責補上「當初為什麼」。每次落地都有人點頭。

① 蒐集：檔案 → 資料庫

Stop hook 每回合從上次讀到的位置往下讀，濾掉工具輸出跟系統訊息，只留你跟 AI 真的說的話。原文存一份，另外切詞存一份給搜尋用。

② 產出：資料庫 → 檔案

卡片匯出成 JSONL，AI 把頁面寫在另一個工作目錄裡（你自己的 clone 完全不動）。審核頁看的是檔案，不是資料庫，所以你在頁面上改、用 IDE 改、叫 AI 改，改的都是同一份。

③ 回流：檔案 → 資料庫

PR 合併後，sync 直接讀 main 上的版本（不是讀別人硬碟上的工作檔），寫回本機的卡片跟頁面，再切一次詞進索引。文件是就地更新的，舊版本留在 git 歷史。

憑什麼找得到

搜尋不是模糊比對，是三條明確的規則。

你什麼時候會用到它

你平常不會自己打搜尋。用到它的是 AI，在兩個時機：你問「我們之前為什麼改成不中斷？」，它去翻你的開發記憶；你叫它寫文件，它搜記憶找「設計考量」要用的「為什麼」。兩個時機都是丟一串字去搜，這一節講的就是這串字怎麼在你的紀錄裡對上。

中文為什麼要特別處理

搜尋像書後面的索引頁：先把每個詞登記起來，查的時候翻索引。英文有空白，一看就知道詞在哪裡切；中文沒有空白，搜尋引擎不知道「更新中介表的狀態」要從哪裡切，只好整句登記成一個詞。

不處理：整句登記成一個詞 更新中介表的狀態 ✕ 查「中介表」對不上
bigram：每兩個相鄰的字都登記一次，不用字典 更新新中中介介表表的的狀狀態 ✓ 查「中介表」→ 中介、介表都在
unigram：每個單字也登記一次 更新中介表的狀態 ✓ 只查「表」也找得到

用你的情境走一遍

查詢時怎麼比對

問句不會跟記憶裡的字一模一樣，所以整句跟每個小塊同時拿去比，命中越多排越前面。「的」「是」這種單字會被丟掉，只會製造雜訊。

搜尋片段是原文，不是切碎的內容。 資料庫裡存兩份：原文給人看，切過詞的只給比對用。所以你看到的是「因為佔位符而拋[例外]，要找出…」，不是「拋例 例外 外要」。

為什麼是兩字一塊＋單字，不是真的斷詞

真正的斷詞器（jieba 這類）靠詞庫認得「測評點數」是一個詞。詞庫要維護，遇到新詞、專有名詞、打錯字就認不出來，而且要另外編譯安裝。

兩字一塊不需要任何詞庫——重疊切法保證任何相鄰兩字都會變成一個 token，所以不必知道詞的邊界在哪。代價是索引大約變 1.8 倍，而且會有誤中（查「中斷」可能撈到「途中斷了」），靠排序壓下去。

兩字一塊叫 bigram，單字叫 unigram。用空間換掉詞庫，是中文全文檢索最常見的無依賴解法。

為什麼後來加上單字（unigram）

代價：索引從 19.6 MB 變 27.4 MB（約 +40%）。升級時舊索引會自動重建——原文都存在表裡，是純本機操作，實測 0.9 秒。隊友更新 plugin 後不用做任何事。

bm25 到底在算什麼

上面表格裡那個「相關度」就是 bm25，全文檢索的標準排序公式，SQLite 內建。它同時算三件事：

它在問規則白話
出現幾次 越多次越相關，但會飽和 出現 5 次比 1 次相關，但 50 次不會比 5 次相關十倍。這樣把關鍵字灌一百遍的垃圾文才贏不了

bm25 回傳的是負數，而且越負越好。這裡踩過坑：正負號寫反，越不相關的排越前面。命中率 20% → 40% 有一半是修這個修回來的。

為什麼不用「語意相似度」

另一條路是把每段文字丟進模型變成一串數字（向量），再用 cosine similarity 比兩個向量的夾角——夾角越小越像。好處是「中斷」找得到「halt」「停住」，換句話說也找得到。

你的記憶裡到處是 sapStatus、@Transactional、erpDocType 這種字串，那正好是 bm25 的強項、向量的弱項。加上不用裝任何模型，第一版就先這樣。

正解其實是兩個一起用。 業界作法叫 hybrid search：bm25 一份排名、cosine 一份排名，再把兩份融合。不是二選一。 這是之後的事——但要先有評測集，否則加上去是變好還變壞根本不知道。

一句話帶走

切詞用 bigram ＋ unigram，因為不想依賴詞庫、又要單字也搜得到；排序用 bm25，因為不用裝東西又講得出道理；向量這次沒用，因為要先裝模型，而且對程式碼識別字不見得比較準。

四個比較不明顯的選擇

為什麼用 SQLite 不用 PostgreSQL

資料是每個人自己的，沒有共享需求——共享的部分走 git。SQLite 就是一個檔案，FTS5 還內建全文檢索。用 PG 等於要每個隊友多裝一個資料庫服務，只為了存自己一個人的資料，不划算。但這個檔案要備份：舊對話（Claude Code 預設 30 天就刪掉原始對話檔）跟個人模式的卡片只存在這裡，不是刪掉重建就好。

為什麼用 git worktree

要在不干擾你的情況下改檔案。git stash 會動到你的工作區，另外 clone 一份又要重抓整個 repo。worktree 共用同一個 .git，但有獨立的工作目錄跟分支——開在你的 repo 隔壁，你完全感覺不到。

為什麼審核頁要 token

它是一個真的 HTTP server。雖然只綁 127.0.0.1，但同一台機器上的任何程式都連得到。所以每次啟動產生一組 UUID，第一次開頁時換成 SameSite=Strict 的 cookie——瀏覽器不會幫別的網站送這個 cookie。

為什麼 JSONL 不用一般 JSON

一個大 JSON 陣列，兩個人各加一筆就會在同一行衝突。JSONL 一行一筆、只在檔尾 append，git 會把兩邊的新行都收下。再加上一人一月一個檔，連碰都碰不到彼此。這個在測試裡真的 merge 過兩個 branch 驗證。

唯一會撞的是同一個人同時開兩個 PR、兩邊都有新卡片：兩邊都在同一個檔尾加行，後 merge 的那個會衝突。解法永遠是兩邊都保留——行的順序沒有意義，少留一邊，那幾張卡片就悄悄從團隊 repo 消失。依序做（前一個 merge 後才開下一個）不會撞，因為開工作區前會先抓最新的 main。

整條路上只有三件事需要你：對 AI 提議的卡片點頭、說要寫哪個主題的文件、在審核頁按那兩個鈕。其他全部是程式在跑，而且沒有一個是常駐的——hook 跑完就結束，審核頁關掉就沒了。

隊友把記憶拉回本機一個指令：sync 終端機

審核頁、IDE、對話三種改法改的是同一個檔案；同時改到會跳出「重新載入 / 保留我的版本」，不會默默蓋掉。

文件到底從哪裡來

這是整個設計最容易做錯的一步，而我們真的做錯過一次。

錯的做法：只讀對話

對話 → 卡片 → 一張卡片一頁

產出長這樣：
「原因／決定／放棄」×5，
五件互不相關的事

看起來像文件，其實是一疊便利貼。因為對話裡只有「當初為什麼這樣選」，沒有「這東西現在怎麼運作」。

對的做法：以程式碼為主

① 程式碼　端點、欄位、驗證、排程、狀態值
② 既有文件　同主題有就更新，不另開一頁
③ 卡片　只補「為什麼」與「Known Issue」

一份沒有 payload 的 API 文件等於沒寫。而 payload 只存在程式碼裡。

差別有多大？同一個主題，第一次只讀對話產出五頁碎片；改成讀程式碼之後，產出一頁有完整 request／response JSON、情境對照表、重跑行為的規格。

為什麼一定要回去讀程式碼

因為另外兩種來源，本質上都會跟程式碼走散：

來源它記的是什麼時候會對不上怎麼處理
開發紀錄 討論當下的提案：打算叫什麼欄位、打算用哪個值 實作時改了名字或改了做法——這很常見，而且完全正常 只拿它寫「為什麼」，欄位與數值一律回去讀程式碼
既有文件 寫下那一刻的狀態 程式改了、文件沒人回頭改（排程時間、欄位、狀態值最常見） 發現不一致就以程式碼為準，並在文件裡標出來
程式碼 現在真正在跑的東西 不會對不上——它本身就是標準 第一來源

紀錄記提案，程式碼記事實。 兩者對不上時一律以程式碼為準，並在文件的「Known Issue」標明——這樣下一個人不會以為是 bug。這在實際跑的時候真的會發生，而且不是誰的疏失，是文件與程式碼本來就會隨時間分岔。

一頁文件該長什麼樣

段落內容為什麼不能省
開頭一句這份在講什麼 ＋ 觸發條件（排程、誰呼叫）讀的人要先知道自己來對地方沒有
整體流程mermaid 圖，一眼看完資料從哪到哪跨系統時文字講不清楚
階段一、二、三…照執行順序講成故事這是「文件」跟「筆記」的分界
真實 payload完整 request／response JSON，含條件必填的各版本範例讀的人會照著打
情境對照表情境／處理／DB 更新／重跑行為出事時第一個被問的就是「能重跑嗎」
設計考量來自卡片：為什麼是這樣擋掉半年後有人重走死路
Known Issue過渡方案、待改善、已知不一致不寫的話下一個人會以為是 bug
維運怎麼確認正常、出錯去哪看、怎麼重跑oncall 半夜要看的就是這段

「一個決定」是文件裡的一個段落，不是一頁文件。 這是最重要的一句話。

為什麼中間要有一層整理

紀錄不是文件

一年下來幾千則紀錄沒人讀得完。中間這層由 LLM 整理成一頁一個主題，人跟 AI 都先讀它，讀不夠再往下挖原始紀錄。

互相連結，同一件事只寫一處

每次 ingest 會同時更新 README 索引跟相關頁面。頁面就地改寫，舊版本留在 git 歷史；被推翻的決定寫成一張新卡片，標明取代了哪一張。

三層各自負責什麼

借自 LLM Wiki 的結構，但每一層的規則都不一樣——這正是它能長期維持正確的原因。真正的第一手事實在第四個地方：程式碼，那在另一個 repo，不屬於這三層。

為什麼要分三層

原始層不可改，所以任何一句話都追得回源頭。整理層可以改寫，所以文件能一直維持正確而不用擔心弄丟歷史。規則層獨立，所以要改 AI 的行為只要改一份 markdown，不用改程式、不用重新發版。

兩個方向

往下找：越往下越細、越沒整理過，但越接近當時真正發生的事。先看整理過的答案，不夠再往下挖。
往上長：越往上越濃縮、讀的人越多。每上一層都有人確認過，所以錯的東西不會自己爬上去。

這三層不是同時都在用的。「往上長」是寫文件的時候，「往下找」是查東西的時候。而規則層只服務寫入——AI 寫之前必讀，讀的人完全不需要知道文件是照什麼規則寫的。

這一層裡面有什麼誰寫誰讀能不能改
規則層 schema.md（怎麼寫文件、來源優先序）、repos.yaml（哪些 repo 屬於哪個產品） 人 只有寫入時：AI 每次動筆前必讀，查東西時完全不碰 隨時改。改這裡＝改 AI 的行為，不用碰程式
整理層 README.md 唯一索引、spec/ 主題文件、maintenance/ SOP AI 寫，人在審核頁核准 兩邊都用：寫入時產出，查東西時第一個被讀（搜尋權重 ×3） 可以改寫：就地更新，舊版本留在 git 歷史
原始層 records/*.jsonl 卡片；本機的完整對話 自動蒐集，卡片由人確認 寫入時一直在累積；查東西時是最後的退路（權重 ×2 / ×1） 只增不改。決策變了寫新的一筆，指向舊的那筆

常見的誤會：寫文件時讀的不是原始層

三層看久了很容易以為流程是「讀原始層 → 經文件層轉譯」。不是。原始層在寫文件時只是配角，第一來源是程式碼。

讀什麼規則層程式碼文件層原始層
原始層累積 不讀，只寫 — — — 一直在寫
寫文件 四個來源 ① 說明書 ② 事實 ③ 避免重複 ④ 只補「為什麼」
查東西 由上往下 完全不碰 都查不到才翻 ① 先看這裡 ② 不夠再往下

為什麼這個差別重要：只讀原始層寫出來的就是決策摘要，不是規格文件。因為原始層裡沒有這些——

文件必須有的在原始層嗎真正在哪
API 的完整 payload❌request / response DTO
必填、格式、值域❌validation annotation
cron 排程❌deploy/env-*.sh
狀態值 1 / 3 / 4❌enum
為什麼選這個方案✅只有這個在原始層

文件層不是轉譯器

規則層 ＝ 說明書（怎麼轉）
LLM ＝ 轉譯的人
文件層 ＝ 轉出來的東西

文件層是產出，不是中間的加工站。真正在轉譯的是 LLM，而它照規則層的指示做。

一句話帶走

寫入時讀規則層當說明書、讀程式碼當事實、讀原始層補「為什麼」，產出文件層。
讀取時只往文件層去，不夠才往原始層挖，規則層完全用不到。

規則層是這個設計最容易被低估的部分。 「程式碼跟卡片衝突時以程式碼為準」「API 文件一定要附完整 payload」「不能寫密碼跟個資」——這些都寫在 schema.md 裡，是純文字。團隊想調整 AI 的產出風格，改那份檔案就好，不需要工程師改程式、不需要重新發版、所有人下一次整理就會照新規則做。

這個設計借了什麼

核心想法來自 Karpathy 的 LLM Wiki 跟 nashsu/llm_wiki：不要每次問問題都從頭翻原始資料，而是讓 LLM 維護一層整理過的內容，人只負責 curate。我們把它從「讀文件」改造成「寫開發文件」——而這個改造，讓其中好幾條規則必須換掉。

最大的差別：原始層會自己動

llm_wiki 的原始層

PDF、網頁、筆記
不可變——你不餵新的，它永遠是那樣
而且它就是事實本身

所以「wiki 不准寫原始素材裡沒有的東西」這條規則是對的：素材是唯一的事實來源。

我們的原始層

開發對話、決策紀錄
只增不改，但它不是事實
真正的事實在程式碼，而程式碼天天在變

所以同一條規則照搬過來就會出事：紀錄記的是當初的提案，實作時改了名字或做法很正常。照紀錄寫規格，寫出來的就是沒發生過的版本。

結論：我們多了一層 llm_wiki 沒有的東西——程式碼，是第一來源，而且是活的。紀錄從「唯一事實」降級成「解釋為什麼的旁證」。這一條決定了後面所有的取捨。

原封不動借來的

概念原本我們
分層 原始素材（不可變）→ LLM 維護層 → 規則檔 一樣的三層，只是上面多掛了程式碼當第一來源
規則寫在 markdown 改規則檔就改 LLM 行為，不用改程式 一樣：schema.md。改來源優先序、改文件骨架都不用發版
唯一索引 index.md，LLM 查東西的入口，每次 ingest 都更新 README.md，而且 CI 強制：沒被索引到的文件直接 lint 失敗
兩步 ingest 先分析要動哪些頁，再產生內容 一樣，而且分析結果一定要作者點頭才動筆
人 curate、LLM maintain 人決定方向，LLM 做整理跟記帳 一樣，再加上本機審核頁跟 PR，改了什麼都看得到
Lint 壞掉的連結、孤兒頁、矛盾 一樣。壞連結跟孤兒頁（沒被 README 索引到的文件）是程式查，語意矛盾要 AI 讀
問答回填 有價值的答案存回去變成一頁 不一樣：答案存成一張卡片（原料），不會一個答案變一頁。文件是主題完成時才一次寫一份

借了但改掉的

概念原本改成為什麼
sources[] 溯源 每頁列出支撐它的原始素材，不准寫素材裡沒有的 來源優先序：程式碼 > 既有文件 > 紀錄。紀錄只支撐「設計考量」與 Known Issue 兩節 照原規則走，永遠寫不出 payload、排程、狀態值——那些不在對話裡
frontmatter 每頁開頭一段 YAML：type、status、sources[] 文件不放。紀錄 JSONL 保留結構化欄位 GitHub 會把它渲染成一大張表格佔滿第一屏。給人讀的東西不該長那樣
[[雙括號連結]] 頁面互連，給 LLM 跟 Obsidian 用 改用一般相對連結 ./spec/x.md GitHub 不會把雙括號變成連結。讀的人點不動，等於沒連
一個主張一頁 概念、人物各自一頁，細碎但好連 一個主題一頁，決定變成頁面裡的一節 照原規則做出來是一疊便利貼。文件要有故事線才讀得下去
entity 頁 人物、概念各自一頁 改成資料表、API、queue、外部系統，而且不另開頁：dm entities 從卡片列出誰讀誰寫，還沒有文件寫到的，就在用到它的流程文件裡補一節 一張表一頁的話，素材不足時會寫出兩行的空頁

刻意不採用的

連帶刪除

原作刪掉來源會連帶清掉衍生頁。我們的紀錄只增不改，這個語意對不上——決策被推翻是「標記取代」，不是刪除。刪掉的話後面的人只會看到結論，不知道曾經試過別的路。

向量檢索

原作預設用 embedding 找相關頁。我們第一版只用關鍵字：內容裡大量是程式識別字，那正好是向量的弱項；而且要每個隊友多跑一個模型服務。

我們加上去的

素材自動來

原作要人工餵文件、PDF。我們從開發對話跟 git 自動收，人只負責確認。不用「記得去寫文件」是整件事成立的前提——靠自律的流程都會死。

團隊共享與把關

原作是單人本機知識庫。我們加了 PR review、CI、gitleaks 機密掃描、跨 repo 的產品對照表。而且 AI 不能 push，送出永遠是人按的按鈕。

文件會說自己過期

頁面記著它描述哪些程式檔與分支，那些檔案被改過就標出來。原作的素材不是程式碼，沒有這個問題；我們的素材天天在變，沒有這層就等著文件說謊。

中文搜得到

原作是英文語境。中文沒有空白，整句會被當成一個 token，所以自己切成兩字一塊再加單字；還有評測集量 Recall，不靠感覺。

記住幾件事

圖書館是正本，日記要自己備份

GitHub 上的團隊 repo 是文件跟卡片的正本，換電腦時同步一次就回來。但你電腦裡的資料庫還存著舊對話——Claude Code 預設 30 天就刪掉原始對話檔，之後只剩這一份；個人模式的卡片也只在這裡。所以要備份，不能當成隨時可刪的索引。

整串當成一塊 發票作廢流程 搜「作廢」✕ 找不到
兩個字切一塊 發票票作作廢廢流流程 搜「作廢」✓ 找到

中文要切成小積木

中文每兩個字切成一塊，搜尋才找得到。同一份資料，原本的斷詞搜「例外」只找到 3 筆，切成小積木後 12 筆全中。

跨 repo：資料表是十字路口

同事第一天要做什麼

1　裝 bun
brew install bun hook 跟 MCP server 都用 bun 啟動，必須在 PATH 裡。gh 也要登入（提交與開 PR 用，個人模式不用）。
2　裝 plugin
claude plugin marketplace add … ＋ plugin install dev-memory Codex 的話還要在 /hooks 信任一次，然後重開 session。
3　clone 文件庫（個人模式跳過）
git clone …/104mis-billing-doc-test ~/project-other/… 這是團隊共用的那一份。clone 到哪都可以，下一步會告訴 plugin。
4　跑一次 setup
dm setup --repo ~/project-other/104mis-billing-doc-test 這一步做完就能用了。它會建 ~/.dev-memory、建空的 memory.db、把既有對話灌進索引、從 main 同步隊友的文件，最後逐項檢查環境。只想自己用就跑 dm setup（不帶 --repo），這是個人模式：一樣收對話、能搜尋、能存卡片，只是不寫文件、不送 PR。

先裝好

一個工具箱，兩份說明書

裡面的東西兩邊共用。Claude Code 看 .claude-plugin/，Codex 看 plugin.json。裝的時候打 dev-memory@104mis-plugins。

Codex 第一次要你按「信任」，它才會開始記。

再加一行 dm

平常用不到——這些事講一句話就會發生。但除錯、想自己下指令的時候會需要它。加進 ~/.zshrc：

dm() { bun "$(ls -d ~/.claude/plugins/cache/104mis-plugins/dev-memory/*/src/cli.ts | sort -V | tail -1)" "$@"; }

寫成函式不是為了好看。cache 裡會同時留著好幾個版本，寫成 alias dm='bun …/*/src/cli.ts' 的話 * 會展開成多個路徑，bun a b 只跑第一個——也就是最舊的那版，而且不會有任何錯誤訊息。上面那行用 sort -V | tail -1 明確挑最新版。

裝好之後跑 dm setup，它會逐項檢查缺什麼，缺的直接告訴你要跑哪一行。

理由說明
關鍵字已經夠用 文件是照主題寫的，查「測評點數」「sap-create-bu-data」這種詞本來就對得上。真正靠同義詞才找得到的情況，目前沒遇到幾次

導入成本壓在最痛的那一刻 要隊友裝 plugin 已經要說服一次，再加上「還要裝一個本機模型服務、吃幾 GB 磁碟、常駐記憶體」，推廣會卡住
沒有評測集就不知道有沒有變好 加上去可能更準，也可能被無關的相似內容洗掉排序。沒量測就不該加
不是不可逆 原始文字都在本機資料庫，要開的時候重跑一次索引就有，不用重新收資料

什麼時候會改變主意：評測集補到 30 題，而且實測關鍵字的 Recall 卡住上不去；或是開始出現大量「我知道討論過但想不起來當初用什麼詞」的情況。到那時做法也不是二選一，而是 hybrid search——關鍵字一份排名、向量一份排名，兩份融合。

要說服別人時，這六個理由依強度排序

上面那張表講的是「現在為什麼不需要」。真的被追問「為什麼不套 embedding」，「本機跑不動」是最弱的理由——它聽起來像做不到。下面才是設計理由，最強的在最前面。

1 搜尋結果的消費者是 LLM，不是人。embedding 的價值在於「使用者打模糊的字，系統猜他要什麼」。但這裡打字的是 agent：它會自己換同義詞重搜三次、先讀 README 再決定關鍵字、拿搜到的識別字再搜一輪。語意那一層已經在 agent 腦袋裡了，再塞一個小模型進去，是拿一個弱兩個數量級的模型去做同一件事。
2 這裡的 query 大宗是識別字，精準比對是特性不是缺陷。實際會搜的是 BuRecordCountRequest、erp_data_record、ChainedTransactionManager、cron(35 00 * * ? *)。這些是罕見詞，bm25 天生給它們最高權重；embedding 會把 BuRecordCountRequest 跟 BuRecordCountResult 壓到幾乎同一個點——但這兩個在文件裡是不同階段。embedding 擅長模糊，我要的是精確。
3 可除錯，而且錯得出來。真的發生過：中文搜不到一段話的最後一個字。能定位到「只切 bigram 沒切 unigram」，修完查「表」從 341 筆變 423 筆，有數字可比。換成向量，這個 bug 不會被發現——它只會變成「有時候搜不太準」，然後沒有下一步。bm25 的分數拆得開：哪個詞命中、幾次、文件多長；向量距離拆不開。
4 零依賴＝裝得起來＝有人用。plugin 是 git clone 裝的，沒有 node_modules。FTS5 是 SQLite 內建、bun:sqlite 是 Bun 內建，整條搜尋路徑的第三方依賴是 0。要 embedding 就要模型檔＋runtime＋向量索引，這三個都是「同事 clone 完跑不起來」的來源。團隊工具的採用率上限，是它的安裝成功率。
5 決定論：索引隨時能重建，向量不行。索引是派生層、records/ 才是原始層，所以換切詞方式只要 rebuild 一次（實測 0.9 秒）。向量只有在同一個模型、同一個版本下可比：同事 A 裝 v1.5、B 裝 v1，索引就不能共用、不能一起 commit、結果不可重現。寫入端也一樣——FTS5 insert 是微秒級、同步跑在 hook 裡沒感覺，每一筆都要 embed 就是幾十到幾百 ms。
6 規模不對，瓶頸不在檢索。embedding 的收益曲線要到「幾十萬份文件＋自然語言問句」才變陡。這裡是一條產品線的量級，關鍵字的 Recall 已經接近可用上限。真正的瓶頸是文件本身寫得好不好——把工程預算花在寫出一篇有故事線的規格，回報遠大於把 Recall 從 0.85 推到 0.88。

雲端 embedding API 直接出局。那等於把公司程式碼片段跟對話紀錄送出去。要避開就只能本地跑，於是繞回第 4 點——所以這不是懶得接 API，是接了就違規。

誠實的反面：什麼時候關鍵字會輸

先自己講，比被問到才講好。真正會輸的場景是：「我要找那個處理退款失敗重試的東西」，但你完全不記得任何識別字，而且文件裡用的詞跟你腦中的詞不一樣——這種 query 現在搜不到。緩解有兩層：agent 會自己改寫 query 重試，而且 README 是唯一索引，真的找不到就整份讀完再決定。

報告時的一句話

檢索層要的是精確、可解釋、零依賴、可重建；語意理解那一層交給已經在現場的 LLM 做。架構上 records/ 是原始層、索引是派生層，要加 hybrid search 不用動資料，多一張表就好——所以這不是放棄 embedding，是先做了那個不加也能用、加了也不用重來的部分。
