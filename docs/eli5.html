藍框是要你點頭的確認點；綠色那一步只有你能做。

三個名詞是什麼誰寫放在哪
對話 你跟 AI 講過的話，原始素材 自動收，不用做事 只在你自己的電腦，不提交

為什麼要做

記憶會蒸發

對話紀錄預設 14 天就清掉。半年後想問「當初為什麼這樣決定」，沒有人答得出來，只能重新踩一次坑。

文件是額外工作

做完功能還要再寫一次文件，沒有人有動力。寫完了，程式碼一改又過期，也沒人回去更新。

知識散在各個 repo

一個功能橫跨 batch、api、frontend。改了一張資料表，誰在讀它、會影響誰，得靠人記。

原本的工具搜「例外」 找到 3 筆 ✕ 漏了 9 筆
實際上有 12 筆 ✓ 現在 12 筆全中

搜不到就等於沒有

原本的記憶工具不會斷中文，搜「例外」只找到 3 筆，實際有 12 筆。找不到的記憶，跟沒記一樣。

它怎麼運作

第 1 步

自動記日記

每講完一回合，對話就存進你電腦裡的 memory.db。原始對話只留在你這台。這一步純粹是程式在搬資料，沒有用到 AI。

搬的是對話紀錄檔，不是設定檔：~/.claude/projects/*/*.jsonl 跟 ~/.codex/sessions/…/rollout-*.jsonl。這兩個工具本來就會把每個 session 寫成 JSONL，plugin 只是照 byte offset 增量讀新增的行並記住讀到哪。settings.json 完全沒碰。

存進去時，中文兩個字一塊 例外外處處理
查「例外」 例外 找到 12 筆，跟逐字比對一樣多
程式名字整個留著，也拆開 sapStatus→ sapstatus
第 2 步

中文也搜得到

問 AI 以前做過什麼，它會先翻這本日記。中文、英文、程式名字混在一起也找得到。翻找本身是資料庫在做，AI 只負責把找到的東西講給你聽。

不是 LIKE '%例外%'，是 SQLite 的 FTS5 全文檢索：where fts match ? order by bm25(fts)。LIKE 要逐筆掃全表而且沒有相關度；FTS5 是倒排索引，查 token 直接命中，再用 bm25 排序。

第 3 步確認點 ①

挑出重點卡片

叫 /mem-save 或 /wiki-ingest，AI 把對話濃縮成卡片——一張卡片就是一個決定，只寫三件事：為什麼、決定什麼、放棄了什麼。你刪改後才留下。

第 4 步確認點 ①

讀程式碼，給你骨架

AI 去讀 controller、DTO、enum、排程設定，然後列出這份文件打算長什麼樣：分幾節、哪節有 payload、哪節有圖。你點頭，它才動筆。

第 5 步確認點 ②

在審核頁改到滿意

瀏覽器自動打開本機審核頁。一次看全部檔案、跟 main 比、看每句話的來源紀錄。你改、叫 AI 改、用 IDE 改都行。

第 6 步

你自己按送出

在審核頁按「送出 PR」，或自己打 dev-memory publish。PR 作者是你本人。AI 從頭到尾不會替你 push。

第 7 步

隊友同步，就搜得到

PR 合併後，隊友 sync 一下，不管用 Claude Code 還是 Codex，都查得到你的決定。

那我到底要做什麼

照平常的方式用 Claude Code 或 Codex 就好，什麼都不用改。你只會在幾個時機開口，每次都只是一句話。

照常工作→ 對話自動存檔→ AI 問「要存嗎」你點頭→ 說「寫一份文件」→ 它去讀程式碼→ ① 確認骨架→ ② 審核頁按兩個鈕

綠色是你主動開口——整條路線只有這一步。藍框是它停下來問你，你回一句話就好。白色的完全不用管。

哪些自動、哪些要你點頭

最容易誤會的一點：「存對話」跟「存卡片」是兩件不同的事。

誰觸發你要做什麼為什麼這樣設計
對話存檔 完全自動（Stop hook，每講完一回合） 什麼都不用做 只存在你電腦裡，不可逆也無害。索引裡那兩千多筆對話，你一次都沒開口過
卡片 AI 會主動提議，但要你點頭 說一句「好」，或改一改再存 卡片會進團隊 repo、只增不改，而且會變成未來文件的「設計考量」——錯的卡片比沒有卡片更糟
寫文件 只有你能開口 說「幫我寫一份〈主題〉的文件」 只有你知道現在這個主題值不值得寫成一頁

你不用記得要存卡片。 每個 session 開始時，plugin 會告訴 AI：「做出決定時——原因、決定了什麼、放棄了什麼——主動提議存起來」。所以是它問你，不是你想起來。而 mem-save 的規則寫死一句：沒給使用者看過的卡片，不准存。

你會講的話

下面五句裡，真正要你主動開口的只有第三句（寫文件）。第一句是回應 AI 的提議，第二句就是平常問問題，最後兩句很少用。用平常講話的方式講就好，對應的 skill 自己會被叫起來。

想要確定叫到它，就打斜線指令：/dev-memory:wiki-ingest。格式是 /plugin名:skill名，四個都可以叫：mem-save、mem-setup、wiki-ingest、wiki-lint。用講的比較自然，但關鍵字沒對上時斜線指令是確定的。

AI 問你要不要存
好，存吧 通常是 AI 先開口問。mem-save 會起草一張卡片：原因、決定、放棄了什麼，印出來給你看，你說「可以」才存進本機。約 30 秒。
它沒問但你覺得值得記，也可以自己講「把這個決定存起來」。
想查以前怎麼決定的
我們之前為什麼改成不中斷？ 這句不用特別交代，直接問就好。它會先翻記憶（文件 → 紀錄 → 原始對話），翻不到才去讀程式碼。答完如果還沒有對應的文件，它會問你要不要順手寫一份。
功能做完，要留下文件
幫我寫一份測評點數拋轉 ERP 的文件 wiki-ingest：讀程式碼 → 給你骨架 → 寫文件 → 開審核頁。中間停兩次等你回話，全程約 10 分鐘。這是唯一會產生 PR 的一句話。主題要具體：一支批次、一條資料流、一個子系統。
文件放一陣子了
幫我檢查文件 wiki-lint：壞連結、沒人連過去的孤兒頁、沒寫來源的內容、程式碼改了但文件沒跟上。一個月跑一次就夠。
裝好了，或壞掉了
幫我設定 dev-memory mem-setup：檢查 bun／git／gh／索引／團隊 repo，缺什麼直接告訴你要跑哪一行。裝完跑一次，之後只有出問題才用得到。

第二句以外的四句，你不講它就不會做。沒有背景程序在偷跑，也不會自己開 PR。唯一永遠在動的只有「每回合把對話存進本機」，那一步不花 AI 額度。

多久整理一次？

你的節奏建議為什麼
做決定的當下 AI 問你就點頭 卡片很便宜，寧可多存。它是之後文件「設計考量」那一節的來源

它會先去讀程式碼

給骨架之前，它已經讀過 controller、DTO、enum、entity、排程設定。用 git show 讀，不會切你的分支——那是你正在工作的 repo。

本機 repo 在哪，查 ~/.dev-memory/config.toml。跑 dm repos 會自動掃常見目錄並列出找到沒有，缺的直接印出要貼的那一行。

四種動作

新增文件　沒有任何一頁講這件事
更新既有文件　已經有，這次是補充
補一節　只動其中一段
不動　已經寫過了

看到「不動」是好事，代表它沒有重複寫一遍。

確認點 ②：審核頁怎麼用

這是唯一一個你會離開對話視窗的地方。它會印一個 http://127.0.0.1:隨機port/?token=… 的網址並自動開瀏覽器——只有你這台連得到，網址帶 token，關掉視窗就結束。

1 左邊那一排是檔案，不是卡片。常見誤會：看到好幾個會以為要挑。不用挑——文件本體、紀錄原文、README 索引，少了任何一個就會斷掉，所以它們一起 commit。真的不想要某一頁，按「捨棄這頁」。
2 四個分頁，至少看前兩個。「編輯 / 預覽」讀內容；「跟 main 比較」看到底動了什麼，更新既有頁面時最有用；「來源紀錄」是這頁每句話的出處，想確認不是它自己編的就翻這裡；「檢查結果」平常是空的。
3 左半邊直接打字就能改。不用開 IDE。你改、AI 改、你在編輯器裡改，三邊都可以同時進行——外面被改到時頁面會問你要留哪一版。
4 右半邊是隊友會看到的樣子。即時跟著左邊變，就是 GitHub 上的樣子。上面那排小標籤是這個檔案的摘要（文件字數、紀錄筆數之類），不會進檔案，只是給你看的。
5 核准並 commit——commit 在本機，還沒上 GitHub。按不下去代表有檢查沒過，去「檢查結果」分頁，點檔名就跳過去修。金鑰、個資、缺來源都會在這裡被擋下來。
6 送出 PR——這一顆才會 push。會再跳一次確認。按之前是灰的，因為還沒有東西可以送。只有你按得下去，AI 碰不到這顆。

PR 合併之後還有最後一步：跑 dev-memory sync（或跟 AI 說「PR 合併了，幫我跑 dev-memory sync」），合併的內容才會進你的本機索引。這一步不會自己發生——開 session 時自動做的是「補收漏掉的對話」，不是「拉團隊的新文件」。隊友也一樣，各自 sync 各自的。

是一組：只留文件不留紀錄，「設計考量」就追不回去；不更新 README，就沒有人找得到。

順手抓到的三個錯

排程表寫 08:35，程式碼是 05:35
紀錄寫欄位 freeKey，實際是 payload
紀錄寫型別 5/6，實際是 2/3

人工維護的文件會過期，紀錄記的是當初的提案。只有程式碼是事實——這就是為什麼第一來源必須是它。

資料從哪來、存到哪

文件的事實來自程式碼；對話只負責補上「當初為什麼」。每次落地都有人點頭。

① 蒐集：檔案 → 資料庫

Stop hook 每回合從上次讀到的位置往下讀，濾掉工具輸出跟系統訊息，只留你跟 AI 真的說的話。原文存一份，另外切詞存一份給搜尋用。

② 產出：資料庫 → 檔案

卡片匯出成 JSONL，AI 把頁面寫在另一個工作目錄裡（你自己的 clone 完全不動）。審核頁看的是檔案，不是資料庫，所以你在頁面上改、用 IDE 改、叫 AI 改，改的都是同一份。

③ 回流：檔案 → 資料庫

PR 合併後，sync 直接讀 main 上的版本（不是讀別人硬碟上的工作檔），寫回本機的卡片跟頁面，再切一次詞進索引。被取代的頁面留著，但不會出現在搜尋結果。

審核頁 worktree 的檔案；「跟 main 比較」來自 git 上的版本；「來源紀錄」才去本機資料庫撈卡片 直接寫回檔案（停止打字 800ms 自動存）
核准 / 送出 PR worktree 的檔案 commit 在 worktree；送出才 push 並開 PR
CI PR 裡的檔案 不存，只擋：機密掃描＋結構檢查
隊友同步 main 上的版本（用 git 直接讀，不碰別人的工作檔） record（merged）、page，再進 fts

切詞做兩次，而且只做在索引跟查詢上。 存進資料庫的永遠是原文；另外存一份切過詞的給搜尋比對用。查詢時把問句用同樣方式切一次，兩邊才對得起來。所以你看到的搜尋片段是人看得懂的原文，不是「拋例 例外 外要」那種切碎的東西。

本機資料庫隨時可以刪。 正本在團隊 repo，原始對話還在你自己的硬碟上。刪掉重建就好，這也是為什麼不把資料庫檔案提交上去。

憑什麼找得到

搜尋不是模糊比對，是三條明確的規則。

① 中文：兩個字一塊，而且重疊 例外外處處理
② 程式名字：整個留著，另外拆開 sapStatus→ sapstatussapstatus

存進去時怎麼切

中文重疊切成兩字一塊，所以「例外處理」裡面搜「外處」也找得到。程式名字保留完整形式（搜 WAIT_FOR_INSERT 不會誤中更長的那個），同時拆成 sap、status，用其中一段也搜得到。

問「中文的搜尋是怎麼切字的」
整句連在一起 ✕ 沒有一模一樣的句子
中文文的搜尋怎麼切字 ✓ 命中越多詞排越前面

查詢時怎麼比對

問句不會跟記憶裡的字一模一樣，所以整句跟每個小塊同時拿去比，命中越多排越前面。「的」「是」這種單字會被丟掉，只會製造雜訊。

這條規則是評測集逼出來的：一開始要求全部命中，問句式搜尋的命中率是 0%。

排序規則怎麼算為什麼
相關度 標準的全文檢索分數（bm25） 命中越多、文件越短、詞越罕見，分數越高
整理程度 文件 ×3　＞　紀錄 ×2　＞　原始對話 ×1 整理過的答案優先，原始對話是最後才翻的
離你多近 同一個 repo 的內容 ×2 你現在在哪個專案，那個專案的決定更可能是你要找的
已被取代的 完全不列出 頁面留著可追溯，但不該再誤導任何人

搜尋片段是原文，不是切碎的內容。 資料庫裡存兩份：原文給人看，切過詞的只給比對用。所以你看到的是「因為佔位符而拋[例外]，要找出…」，不是「拋例 例外 外要」。

為什麼是兩個字一塊，不是真的斷詞

真正的斷詞器（jieba 這類）靠詞庫認得「測評點數」是一個詞。詞庫要維護，遇到新詞、專有名詞、打錯字就認不出來，而且要另外編譯安裝。

兩字一塊不需要任何詞庫——重疊切法保證任何相鄰兩字都會變成一個 token，所以不必知道詞的邊界在哪。代價是索引大約變 1.8 倍，而且會有誤中（查「中斷」可能撈到「途中斷了」），靠排序壓下去。

這叫 bigram。用空間換掉詞庫，是中文全文檢索最常見的無依賴解法。

bm25 到底在算什麼

上面表格裡那個「相關度」就是 bm25，全文檢索的標準排序公式，SQLite 內建。它同時算三件事：

它在問規則白話
出現幾次 越多次越相關，但會飽和 出現 5 次比 1 次相關，但 50 次不會比 5 次相關十倍。這樣把關鍵字灌一百遍的垃圾文才贏不了
這個詞罕不罕見 只出現在 3 篇的詞，權重遠高於出現在 2000 篇的 命中「測評點數」幾乎確定就是你要的；命中「系統」等於沒講。所以不用自己排除「的、是、了」，它們的權重會自動趨近 0
這篇有多長 除以平均長度 一萬字的文章隨機也會含到你的關鍵字，不該因為字多就自動贏

bm25 回傳的是負數，而且越負越好。這裡踩過坑：正負號寫反，越不相關的排越前面。命中率 20% → 40% 有一半是修這個修回來的。

為什麼不用「語意相似度」

另一條路是把每段文字丟進模型變成一串數字（向量），再用 cosine similarity 比兩個向量的夾角——夾角越小越像。好處是「中斷」找得到「halt」「停住」，換句話說也找得到。

bm25（這次用的）cosine（這次不用）
比什麼 字面上的詞有沒有命中 兩個向量的夾角
要裝什麼 什麼都不用，SQLite 內建 要先裝 embedding 模型（Ollama）或買 API
強項 專有名詞、程式碼識別字、精準比對 同義詞、換句話說
弱項 問「效能問題」找不到寫「太慢」的紀錄 WAIT_FOR_INSERT_MIDDLE_DB 這種字串模型常常認不得
查不到時 印得出命中哪些詞，改得動 只有一個 0.87 的分數，無從下手
成本 每次 <10ms，零 AI 額度 每篇都要先跑一次模型

你的記憶裡到處是 sapStatus、@Transactional、erpDocType 這種字串，那正好是 bm25 的強項、向量的弱項。加上不用裝任何模型，第一版就先這樣。

正解其實是兩個一起用。 業界作法叫 hybrid search：bm25 一份排名、cosine 一份排名，再把兩份融合。不是二選一。 這是之後的事——但要先有評測集，否則加上去是變好還變壞根本不知道。

一句話帶走

切詞用 bigram，因為不想依賴詞庫；排序用 bm25，因為不用裝東西又講得出道理；向量這次沒用，因為要先裝模型，而且對程式碼識別字不見得比較準。

所以這個 plugin 用了什麼

存進去 → bigram 切詞（自己寫的，不靠詞庫）
查詢時 → bigram OR 組合
排序 → bm25 × 種類權重 × 同 repo 權重

就這些。沒有向量、沒有 embedding、沒有模型——所以隊友只要裝 Bun 就能用。

哪些步驟會用到 AI

大部分步驟是純程式，一個 token 都不花。真正用到 AI 的只有「要動腦」的那幾步，而且用的就是你手上的 Claude Code 或 Codex，不需要另外申請 API key。

步驟誰在做花不花 AI 額度
自動記日記 程式：讀檔、寫資料庫、切詞 不花。完全沒有呼叫任何模型
搜尋本身 程式：全文檢索加排序 不花。SQLite 自己算完
回答你的問題 AI 讀搜尋結果，組織成答案 花。就是你原本的對話
讀程式碼＋出骨架（確認點 ①） AI 從對話萃取原因／決定／放棄 花。一次約 1.1k token
整理計畫（確認點 ②） AI 比對現有頁面，決定新增或更新 花。整個 ingest 約 1.3k token 加上寫頁面的內容
寫頁面 AI 依照 schema.md 的規則寫
審核頁、比對 main、檢查機密 程式：本機網頁、git、正規表達式 不花
送 PR、CI 檢查、隊友同步 程式：git、GitHub Actions 不花
檢查文件的矛盾 壞連結、孤兒頁是程式查；語意上的矛盾要 AI 讀過 部分。一次約 850 token

常駐成本：每個 session 約 295 token

裝了這個 plugin 之後，每次開 session 會多出一段簡短的說明（記憶裡有多少筆、目前在哪個 repo、要先查記憶再回答）。四個 skill 的說明書只有被叫到才載入，平常不佔位置。

這是 claude plugin details dev-memory 報的實際數字，不是估的。

沒有背景程序在燒 token

沒有常駐的觀察者、沒有定時任務、沒有「幫你自動整理」的背景 AI。只有你開口要求時才會用到 AI，其餘時間這個 plugin 在做的事都是檔案跟資料庫操作。

原本那套工具的問題之一就是背景一直在耗 token，這次刻意不那樣設計。

用的是你自己的訂閱。 所有 AI 的工作都發生在你已經開著的 Claude Code 或 Codex 裡，不需要另外的 API key、不需要另外付費、公司也不用額外開帳號。換句話說：這個 plugin 不會自己去用 AI，它只是讓你手上的 AI 記得事情。

哪一步在哪裡做

對話裡只挑內容、對計畫。真正的編輯跟審核在瀏覽器，不是在對話視窗裡。

存決策、看骨架、說要加什麼砍什麼確認點 ①，一句話回覆就好 對話裡
AI 寫頁面寫在獨立的 worktree，你自己的 clone 完全不受影響 磁碟上
編輯、預覽、跟 main 比對、看來源、核准、送出確認點 ②，本機網頁，只綁 127.0.0.1 瀏覽器
CI 檢查與 mergegitleaks 掃全 repo，結構檢查掃文件連結與 records GitHub
隊友把記憶拉回本機一個指令：sync 終端機

審核頁、IDE、對話三種改法改的是同一個檔案；同時改到會跳出「重新載入 / 保留我的版本」，不會默默蓋掉。

文件到底從哪裡來

這是整個設計最容易做錯的一步，而我們真的做錯過一次。

錯的做法：只讀對話

對話 → 卡片 → 一張卡片一頁

產出長這樣：
「原因／決定／放棄」×5，
五件互不相關的事

看起來像文件，其實是一疊便利貼。因為對話裡只有「當初為什麼這樣選」，沒有「這東西現在怎麼運作」。

對的做法：以程式碼為主

① 程式碼　端點、欄位、驗證、排程、狀態值
② 既有文件　同主題有就更新，不另開一頁
③ 卡片　只補「為什麼」與「Known Issue」

一份沒有 payload 的 API 文件等於沒寫。而 payload 只存在程式碼裡。

差別有多大？同一個主題，第一次只讀對話產出五頁碎片；改成讀程式碼之後，產出一頁有完整 request／response JSON、情境對照表、重跑行為的規格。

讀程式碼當場抓到三個錯

而且不是理論上的好處——改成讀程式碼的第一天，就抓到既有資料三個錯：

項目舊資料說程式碼實際是為什麼會錯
排程時間 排程表寫 08:35 deploy/env-production.sh：cron(35 21) UTC ＝ 05:35 人工維護的表沒跟上改動
中介表欄位 卡片寫 freeKey payload 卡片記的是當初的提案
型別代號 卡片寫 5 / 6 2 / 3 同上，實作時改了

卡片記提案，程式碼記事實。 兩者衝突時一律以程式碼為準，並在文件的「Known Issue」註明不一致——順便提醒有人去修舊文件。

一頁文件該長什麼樣

段落內容為什麼不能省
開頭一句這份在講什麼 ＋ 觸發條件（排程、誰呼叫）讀的人要先知道自己來對地方沒有
整體流程mermaid 圖，一眼看完資料從哪到哪跨系統時文字講不清楚
階段一、二、三…照執行順序講成故事這是「文件」跟「筆記」的分界
真實 payload完整 request／response JSON，含條件必填的各版本範例讀的人會照著打
情境對照表情境／處理／DB 更新／重跑行為出事時第一個被問的就是「能重跑嗎」
設計考量來自卡片：為什麼是這樣擋掉半年後有人重走死路
Known Issue過渡方案、待改善、已知不一致不寫的話下一個人會以為是 bug
維運怎麼確認正常、出錯去哪看、怎麼重跑oncall 半夜要看的就是這段

「一個決定」是文件裡的一個段落，不是一頁文件。 這是最重要的一句話。

為什麼中間要有一層整理

紀錄不是文件

一年下來幾千則紀錄沒人讀得完。中間這層由 LLM 整理成一頁一個主題，人跟 AI 都先讀它，讀不夠再往下挖原始紀錄。

互相連結，舊的會被標掉

每次 ingest 會同時更新總目錄跟相關頁面；被推翻的決定不刪掉，標成「已被取代」，搜尋時不會再跳出來誤導人。

三層各自負責什麼

借自 LLM Wiki 的結構，但每一層的規則都不一樣——這正是它能長期維持正確的原因。真正的第一手事實在第四個地方：程式碼，那在另一個 repo，不屬於這三層。

為什麼要分三層

原始層不可改，所以任何一句話都追得回源頭。整理層可以改寫，所以文件能一直維持正確而不用擔心弄丟歷史。規則層獨立，所以要改 AI 的行為只要改一份 markdown，不用改程式、不用重新發版。

兩個方向

往下找：越往下越細、越沒整理過，但越接近當時真正發生的事。先看整理過的答案，不夠再往下挖。
往上長：越往上越濃縮、讀的人越多。每上一層都有人確認過，所以錯的東西不會自己爬上去。

這一層裡面有什麼誰寫誰讀能不能改
規則層 schema.md（怎麼寫文件、來源優先序）、repos.yaml（哪些 repo 屬於哪個產品） 人 AI 每次整理前必讀 隨時改。改這裡＝改 AI 的行為，不用碰程式
整理層 README.md 唯一索引、spec/ 主題文件、maintenance/ SOP AI 寫，人在審核頁核准 人跟 AI 都先讀這層 可以改寫。被推翻的頁面標成「已取代」而不是刪掉，搜尋不再列出
原始層 records/*.jsonl 卡片；本機的完整對話 自動蒐集，卡片由人確認 追溯時才往下翻 只增不改。決策變了寫新的一筆，指向舊的那筆

規則層是這個設計最容易被低估的部分。 「頁面要寫原因跟放棄的方案」「不能寫密碼跟個資」「決策被推翻要標記不要刪」——這些都寫在 schema.md 裡，是純文字。團隊想調整 AI 的產出風格，改那份檔案就好，不需要工程師改程式、不需要重新發版、所有人下一次整理就會照新規則做。

這個設計借了什麼

核心想法來自 Karpathy 的 LLM Wiki 跟 nashsu/llm_wiki：不要每次問問題都從頭翻原始資料，而是讓 LLM 維護一層整理過的內容，人只負責 curate。我們把它從「讀文件」改造成「寫開發文件」——而這個改造，讓其中好幾條規則必須換掉。

最大的差別：原始層會自己動

llm_wiki 的原始層

PDF、網頁、筆記
不可變——你不餵新的，它永遠是那樣
而且它就是事實本身

所以「wiki 不准寫原始素材裡沒有的東西」這條規則是對的：素材是唯一的事實來源。

我們的原始層

開發對話、決策紀錄
只增不改，但它不是事實
真正的事實在程式碼，而程式碼天天在變

所以同一條規則照搬過來就會出事——我們真的出過事：照紀錄寫，寫出 freeKey、型別 5/6，實際是 payload、2/3。紀錄記的是當初的提案。

結論：我們多了一層 llm_wiki 沒有的東西——程式碼，是第一來源，而且是活的。紀錄從「唯一事實」降級成「解釋為什麼的旁證」。這一條決定了後面所有的取捨。

原封不動借來的

概念原本我們
分層 原始素材（不可變）→ LLM 維護層 → 規則檔 一樣的三層，只是上面多掛了程式碼當第一來源
規則寫在 markdown 改規則檔就改 LLM 行為，不用改程式 一樣：schema.md。改來源優先序、改文件骨架都不用發版
唯一索引 index.md，LLM 查東西的入口，每次 ingest 都更新 README.md，而且 CI 強制：沒被索引到的文件直接 lint 失敗
兩步 ingest 先分析要動哪些頁，再產生內容 一樣，而且分析結果一定要作者點頭才動筆
人 curate、LLM maintain 人決定方向，LLM 做整理跟記帳 一樣，再加上本機審核頁跟 PR，改了什麼都看得到
Lint 壞掉的連結、孤兒頁、矛盾 一樣。壞連結跟孤兒頁是程式查，語意矛盾要 AI 讀
問答回填 有價值的答案存回去變成一頁 一樣：答完如果還沒有對應文件，會問你要不要順手寫一份

借了但改掉的

概念原本改成為什麼
sources[] 溯源 每頁列出支撐它的原始素材，不准寫素材裡沒有的 來源優先序：程式碼 > 既有文件 > 紀錄。紀錄只支撐「設計考量」與 Known Issue 兩節 照原規則走，永遠寫不出 payload、排程、狀態值——那些不在對話裡
frontmatter 每頁開頭一段 YAML：type、status、sources[] 文件不放。紀錄 JSONL 保留結構化欄位 GitHub 會把它渲染成一大張表格佔滿第一屏。給人讀的東西不該長那樣
[[雙括號連結]] 頁面互連，給 LLM 跟 Obsidian 用 改用一般相對連結 ./spec/x.md GitHub 不會把雙括號變成連結。讀的人點不動，等於沒連
一個主張一頁 概念、人物各自一頁，細碎但好連 一個主題一頁，決定變成頁面裡的一節 照原規則做出來是一疊便利貼。文件要有故事線才讀得下去
entity 頁 人物、概念各自一頁 改成資料表、API、queue、外部系統——還沒做 跨 repo 最需要這個，但素材不足時會寫出兩行的空頁
log.md 變更紀錄 只增不改，固定格式方便 grep 拿掉，改看 git log 與 PR git 本來就在做這件事，多一份會過期的副本沒有意義

刻意不採用的

連帶刪除

原作刪掉來源會連帶清掉衍生頁。我們的紀錄只增不改，這個語意對不上——決策被推翻是「標記取代」，不是刪除。刪掉的話後面的人只會看到結論，不知道曾經試過別的路。

向量檢索

原作預設用 embedding 找相關頁。我們第一版只用關鍵字：內容裡大量是程式識別字，那正好是向量的弱項；而且要每個隊友多跑一個模型服務。

我們加上去的

素材自動來

原作要人工餵文件、PDF。我們從開發對話跟 git 自動收，人只負責確認。不用「記得去寫文件」是整件事成立的前提——靠自律的流程都會死。

團隊共享與把關

原作是單人本機知識庫。我們加了 PR review、CI、gitleaks 機密掃描、跨 repo 的產品對照表。而且 AI 不能 push，送出永遠是人按的按鈕。

文件會說自己過期

頁面記著它描述哪些程式檔與分支，那些檔案被改過就標出來。原作的素材不是程式碼，沒有這個問題；我們的素材天天在變，沒有這層就等著文件說謊。

中文搜得到

原作是英文語境。中文沒有空白，整句會被當成一個 token，所以自己切成兩字一塊；還有評測集量 Recall，不靠感覺。

來源：Karpathy 的 LLM Wiki gist、nashsu/llm_wiki

記住幾件事

圖書館才是正本

GitHub 上的團隊 repo 是正本。你電腦裡的資料庫只是索引，壞了或換電腦，重建一份就好。

整串當成一塊 發票作廢流程 搜「作廢」✕ 找不到
兩個字切一塊 發票票作作廢廢流流程 搜「作廢」✓ 找到

中文要切成小積木

中文每兩個字切成一塊，搜尋才找得到。同一份資料，原本的斷詞搜「例外」只找到 3 筆，切成小積木後 12 筆全中。

跨 repo：資料表是十字路口

每張資料表、每支 API 都有自己的一頁，寫著哪些 repo 在讀、哪些在寫，一看就知道改了會影響誰。圖上的關係只是範例。

兩支筆，同一本日記

同一個 plugin，Claude Code 和 Codex 都能裝。兩邊寫進同一份記憶，換工具也不會失憶。

會動到哪些 repo 跟檔案

全部就兩個 repo 加一個本機資料夾。搞懂這三個，整件事就沒有黑盒子了。

東西是什麼誰有裡面放什麼
dev-memory 工具本身（plugin ＋ marketplace） 安裝時自動 clone 到 plugin cache，你不用管 skill、hook、MCP server、CLI。不含任何記憶資料
104mis-billing-doc-test 文件庫（團隊共用） 每個人自己 clone 一份 spec/ 文件、records/ 紀錄、schema.md 規則、repos.yaml

billing 的各個 code repo 事實來源 你本來就有 寫文件時只讀不寫，用 git show，不會切你的分支

同事第一天要做什麼

1　裝 bun
brew install bun hook 跟 MCP server 都用 bun 啟動，必須在 PATH 裡。gh 也要登入（提交與開 PR 用）。
2　裝 plugin
claude plugin marketplace add … ＋ plugin install dev-memory Codex 的話還要在 /hooks 信任一次，然後重開 session。
3　clone 文件庫
git clone …/104mis-billing-doc-test ~/project-other/… 這是團隊共用的那一份。clone 到哪都可以，下一步會告訴 plugin。
4　跑一次 setup
dm setup --repo ~/project-other/104mis-billing-doc-test 這一步做完就能用了。它會建 ~/.dev-memory、建空的 memory.db、把既有對話灌進索引、從 main 同步隊友的文件，最後逐項檢查環境。
5　補程式碼位置
dm repos 列出 repos.yaml 裡每個 repo 在本機找到沒有。大多會自動找到（掃 ~/project-backend 那幾個慣例目錄比對 git remote），缺的會直接印出要貼進 config.toml 的那一行。

不用裝 claude-mem，也不用任何資料庫伺服器。 memory.db 的 schema 是 dev-memory 自己建的（src/core/db.ts，用 pragma user_version 做版本遷移），跟其他工具沒有關係。第一次跑 setup 就會建好。

裡面的東西兩邊共用。Claude Code 看 .claude-plugin/，Codex 看 plugin.json。裝的時候打 dev-memory@104mis-plugins。

Codex 第一次要你按「信任」，它才會開始記。

再加一行 dm

平常用不到——這些事講一句話就會發生。但除錯、想自己下指令的時候會需要它。加進 ~/.zshrc：

dm() { bun "$(ls -d ~/.claude/plugins/cache/104mis-plugins/dev-memory/*/src/cli.ts | sort -V | tail -1)" "$@"; }

寫成函式不是為了好看。cache 裡會同時留著好幾個版本，寫成 alias dm='bun …/*/src/cli.ts' 的話 * 會展開成多個路徑，bun a b 只跑第一個——也就是最舊的那版，而且不會有任何錯誤訊息。上面那行用 sort -V | tail -1 明確挑最新版。

裝好之後跑 dm setup，它會逐項檢查缺什麼，缺的直接告訴你要跑哪一行。

現在的決定：不裝 Ollama

~/.dev-memory/config.toml 裡 provider = "none"，vector 資料表是空的。這不是「還沒做」，是評估過之後決定現在不需要。

理由說明
關鍵字已經夠用 文件是照主題寫的，查「測評點數」「sap-create-bu-data」這種詞本來就對得上。真正靠同義詞才找得到的情況，目前沒遇到幾次
內容特性不利向量 記憶裡到處是 sapStatus、@Transactional、WAIT_FOR_INSERT_MIDDLE_DB。這種字串 embedding 模型常常認不得，反而是關鍵字的強項
導入成本壓在最痛的那一刻 要隊友裝 plugin 已經要說服一次，再加上「還要裝一個本機模型服務、吃幾 GB 磁碟、常駐記憶體」，推廣會卡住
沒有評測集就不知道有沒有變好 加上去可能更準，也可能被無關的相似內容洗掉排序。沒量測就不該加
不是不可逆 原始文字都在本機資料庫，要開的時候重跑一次索引就有，不用重新收資料

什麼時候會改變主意：累積到 50 題以上的評測集，而且實測關鍵字的 Recall 卡住上不去；或是開始出現大量「我知道討論過但想不起來當初用什麼詞」的情況。到那時做法也不是二選一，而是 hybrid search——關鍵字一份排名、向量一份排名，兩份融合。
